# Game

2D пошаговая игра для Android/Termux, работающая непосредственно в терминале.

Проект ориентирован на самостоятельную реализацию игрового движка без SDL, OpenGL, Vulkan, X11, GTK, ncurses и других сторонних графических фреймворков.

## Цели проекта

- 2D игровое поле в терминале.
- Пошаговая игровая модель: одно действие игрока продвигает игровой ход.
- Собственный игровой движок.
- Собственные правила мира, движения, боя, AI, предметов и сохранений.
- Минимальные системные зависимости.
- Отделение игрового кода от Termux/терминала.
- Возможность тестировать игровую логику без реального терминала.

## Ограничения и зависимости

Проект не использует графические библиотеки и фреймворки:

- SDL / SDL2
- OpenGL / OpenGL ES
- Vulkan
- X11
- GTK
- ncurses
- SFML и аналогичные библиотеки

Для терминальной версии используются только возможности, необходимые для работы обычного терминала Termux:

- `stdin` / `stdout`;
- POSIX `termios` для настройки режима ввода;
- ANSI/VT-последовательности терминала для управления курсором и отображения символов;
- стандартный файловый ввод-вывод для сохранений и данных.

Это означает, что наличие других пакетов в установленном Termux не означает их использования проектом.

## Архитектура

Проект строится по направлению зависимостей:

```text
GAME
  ↓
ENGINE
  ↓
PLATFORM
  ↓
TERMUX
```

Зависимости не должны идти в обратную сторону.

```text
GAME → TERMINAL    ❌
GAME → termios     ❌
GAME → ANSI        ❌
ENGINE → termios   ❌

GAME → ENGINE      ✅
ENGINE → PLATFORM  ✅
PLATFORM → TERMUX  ✅
```

Главный принцип: **игра и ядро движка не знают, что работают в Termux**.

## Engine

Engine содержит механизмы, а не содержание конкретной игры.

Engine знает о:

- `World`;
- `Map` и `Tile`;
- `Entity`;
- компонентах состояния (`Position`, `Health`, `Inventory`, `AI`, `Renderable` и т.д.);
- `Command`;
- `Event`;
- пошаговой модели;
- системах обработки;
- сохранении и загрузке;
- `RenderBuffer`.

Engine не должен содержать знания о конкретных объектах игры вроде `Goblin`, `Dragon`, `Iron Sword` или конкретных квестах. Это слой `GAME`.

## Game

Слой `GAME` использует API движка и описывает конкретную игру:

```text
game/
├── player/
├── creatures/
├── items/
├── maps/
├── combat/
└── quests/
```

Например, игра определяет характеристики монстра и предмета, а Engine предоставляет механизмы перемещения, изменения здоровья, инвентаря, событий и сохранения.

## Entity и компоненты

Для сущностей используется простая модель:

```text
Entity = ID
```

Данные хранятся отдельно и могут комбинироваться:

```text
Position
Health
Inventory
AI
Renderable
```

Например:

```text
Entity 17
  Position
  Health
  Renderable

Entity 23
  Position
  Health
  AI
  Renderable
```

На начальном этапе не требуется полноценный ECS-фреймворк с archetype/sparse-set/query-системой. Сначала используется простое компонентное хранение; более сложная ECS-реализация появляется только при реальной необходимости.

## Systems

Игровое состояние изменяют отдельные системы:

```text
MovementSystem
CombatSystem
AISystem
InventorySystem
DeathSystem
QuestSystem
```

Каждая система отвечает за ограниченную область поведения.

Пример:

```text
Command MOVE_UP
      ↓
MovementSystem
      ↓
проверка карты
      ↓
изменение Position
      ↓
Event ENTITY_MOVED
```

Системы по возможности не вызывают друг друга напрямую. Для связи используется очередь событий.

## Commands

Ввод сначала преобразуется в абстрактную команду.

```text
клавиша
  ↓
TerminalInput
  ↓
Key
  ↓
InputMapper
  ↓
Command
  ↓
Engine
```

Примеры команд:

```text
MOVE_UP
MOVE_DOWN
MOVE_LEFT
MOVE_RIGHT
ATTACK
USE_ITEM
PICKUP
DROP
WAIT
OPEN
TALK
```

Это позволяет получать одинаковые команды из клавиатуры, AI, тестов или системы replay, не связывая игровую логику с конкретными клавишами.

## Events

Для слабой связанности систем используется очередь событий.

Примеры:

```text
ENTITY_MOVED
ENTITY_ATTACKED
ENTITY_DAMAGED
ENTITY_DIED
ITEM_PICKED
DOOR_OPENED
QUEST_COMPLETED
```

Например, `CombatSystem` сообщает `ENTITY_DIED`, а `QuestSystem` самостоятельно решает, изменяет ли это событие состояние квеста.

Такой подход соответствует паттерну Event Queue, описанному в *Game Programming Patterns*.

## Пошаговый цикл

Для этой игры не нужен постоянный real-time update каждого объекта. Игра ориентирована на последовательность действий:

```text
WAIT INPUT
    ↓
COMMAND
    ↓
VALIDATE
    ↓
PLAYER TURN
    ↓
ENEMY TURNS
    ↓
EVENTS
    ↓
RENDER
    ↓
WAIT INPUT
```

Обычный Game Loop разделяет ввод, обновление состояния и отображение. Для пошаговой игры состояние мира продвигается после принятого действия игрока, а не непрерывно по времени. *Game Programming Patterns* отдельно отмечает, что постоянный Update Method плохо подходит для абстрактных игр, похожих на шахматы, где объекты не нужно симулировать каждый кадр.

## RenderBuffer

Engine не выводит ANSI-последовательности непосредственно.

Сначала создаётся логический буфер экрана:

```text
Game World
    ↓
Renderer
    ↓
RenderBuffer
    ↓
Terminal Renderer
    ↓
ANSI
    ↓
stdout
    ↓
Termux Terminal
```

Например:

```text
##########
#........#
#...@....#
#....g...#
##########
```

`RenderBuffer` позволяет отделить игровое состояние от способа вывода.

## Terminal API

Минимальный платформенный API может содержать операции уровня:

```c
terminal_init();
terminal_clear();
terminal_move_cursor(x, y);
terminal_put_char(x, y, ch);
terminal_put_text(x, y, text);
terminal_flush();
terminal_shutdown();
```

Это API принадлежит только слою `PLATFORM`.

## Input API

Терминальный ввод преобразует байты `stdin` в абстрактные клавиши/команды.

`termios` используется для настройки режима терминала, чтобы ввод можно было получать без обязательного нажатия Enter.

Engine не должен обращаться к `termios` напрямую.

## Последовательность разработки

Разработка выполняется вертикальными этапами. Сначала должна появиться минимальная работающая игра, а не полностью абстрактный движок.

### 1. Terminal

Реализовать:

```text
init
clear
cursor
put_char
put_text
flush
shutdown
```

Цель: вывести простое поле и несколько символов.

### 2. Input

Реализовать чтение клавиш через терминальный ввод и `termios`.

Проверить:

```text
W A S D
стрелки
Enter
Escape
```

### 3. RenderBuffer

Создать двумерный буфер символов фиксированного размера.

Цель: сначала рисовать в буфер, затем целиком отправлять его в терминал.

### 4. World

Добавить:

```text
Map
Tile
Entity
Position
```

Игрок становится Entity, а не просто символом `@`.

### 5. Movement

Добавить команды движения и `MovementSystem`.

Поток:

```text
Key
↓
Command
↓
MovementSystem
↓
World
↓
RenderBuffer
```

### 6. Turn System

Добавить строгую последовательность:

```text
PLAYER TURN
↓
ENEMY TURNS
↓
END TURN
```

Одно принятое действие игрока продвигает игровой мир на один ход.

### 7. Enemy AI

Добавить простейший `AISystem`. На первом этапе достаточно элементарного поведения и проверки доступности клеток. Pathfinding добавляется позже, когда будет понятна необходимость.

### 8. Combat

Добавить:

```text
AttackCommand
CombatSystem
Health
Damage
DeathSystem
```

### 9. Items

Добавить:

```text
Item
Inventory
Equipment
```

### 10. Map features

Добавить стены, двери, переходы, уровни и другие особенности карты.

### 11. Save/Load

После стабилизации структуры `World` реализовать сериализацию состояния игры и сохранение на диск.

### 12. Content

Только после готовности базовых систем добавлять большое количество контента:

```text
враги
предметы
карты
NPC
квесты
сюжет
```

## Что сознательно не используется

На текущем этапе не добавляются:

- SDL/SDL2;
- OpenGL/OpenGL ES;
- Vulkan;
- X11;
- GTK;
- ncurses;
- SFML;
- сторонние ECS-фреймворки;
- сторонний графический движок.

Причина — проект должен самостоятельно реализовать игровую логику и терминальный слой, используя только минимально необходимые системные интерфейсы Termux/Linux.

## Ссылки и обоснование архитектуры

- [Game Programming Patterns — Game Loop](https://gameprogrammingpatterns.com/game-loop.html) — разделение обработки ввода, обновления состояния и отображения; обсуждение fixed timestep и роли движка.
- [Game Programming Patterns — Update Method](https://gameprogrammingpatterns.com/update-method.html) — ограничения покадрового Update Method и замечание о том, что он плохо подходит для абстрактных пошаговых игр наподобие шахмат.
- [Game Programming Patterns — Event Queue](https://gameprogrammingpatterns.com/event-queue.html) — применение очереди событий для уменьшения связанности компонентов.

## Принцип проекта

> **Сначала минимальный работающий терминальный прототип, затем движок вокруг реально существующей игры.**

Не создавать лишние абстракции заранее. Каждый новый слой должен появляться тогда, когда он решает реальную проблему проекта.
